## Context

当前前端已经具备数据加载、搜索、标签筛选、排序、收藏和 `basePath` 适配能力，但首页缺少 PRD 中明确提到的 `About` 入口和针对不同空状态的恢复动作。另一方面，`copenclaw` 已能抓取 RSS 并做基础去重，但 HTML 源、数据校验、分片输出、执行摘要与容错仍不完整，难以支撑手动维护流程。

本次变更横跨前端组件与数据更新工具两个模块，因此需要用一份设计统一约束行为边界，但不涉及视觉打磨与复杂自动化平台接入。

## Goals / Non-Goals

**Goals:**
- 补齐首页内的核心说明入口与状态恢复路径。
- 让收藏写入失败时有可理解的反馈，避免静默失败。
- 让 `copenclaw` 能稳定完成“抓取 → 规范化 → 去重 → 校验 → 输出”的手动更新主流程。
- 在数据量增大时生成分片和 `manifest.json`，使前端现有分片加载逻辑真正可用。

**Non-Goals:**
- 不在本次实现中打磨最终视觉样式与动画细节。
- 不接入真实 PR 创建、GitHub API 或在线 LLM 服务。
- 不新增后端服务、数据库或用户系统。

## Decisions

### 1. 首页说明采用组件内轻量弹层
- 选择在 `nav-hoard` 内部实现 `About` 按钮和弹层，而不是新页面或外部文档跳转。
- 原因：PRD 要求所有功能在首页内完成，且该信息主要用于解释收录规则与更新方式。
- 备选方案：跳转 README / docs。放弃原因是会打断浏览流，且在博客嵌入场景下不够自包含。

### 2. 空状态按原因区分，而不是统一“暂无内容”
- 搜索/标签命中为空时，展示“未找到匹配内容”并提供清空筛选动作。
- 收藏视图为空时，展示“还没有收藏内容”并提供返回全部视图动作。
- 数据加载失败保持现有错误态，但补充更友好的恢复提示。
- 原因：不同空状态的下一步动作不同，统一提示会降低可用性。

### 3. 收藏持久化失败时回滚本次切换并显示瞬时错误
- 在收藏写入 `localStorage` 时捕获异常，若失败则回滚本次收藏变更并显示错误消息。
- 对 `QuotaExceededError` 给出更具体提示，其它异常使用通用存储失败提示。
- 原因：比“仅控制台报错”更符合用户预期，也能避免 UI 与持久化状态不一致。

### 4. `copenclaw` 采用分阶段纯 Node 流水线
- 阶段拆分为：读取配置 → 抓取源 → 规范化与提取 → 去重合并 → Schema 校验 → 单文件/分片输出 → 打印统计。
- RSS 使用 `rss-parser`，HTML 使用 `node-fetch` + `cheerio`，不新增额外运行时依赖。
- 原因：复用现有依赖，降低实现复杂度，便于后续替换某一阶段。

### 5. 标签与摘要补全优先使用确定性规则
- 若源内容已有摘要则清洗后保留；若缺失则从正文/标题截取生成。
- 标签优先来自 RSS category / HTML 配置，其次基于标题和摘要中的关键词做轻量推断。
- 原因：PRD 的核心是“可维护的数据流”，不是必须接入在线模型；确定性方案更易离线运行和验证。
- 备选方案：强依赖远端 LLM。放弃原因是会让手动流程依赖密钥、网络和外部服务稳定性。

### 6. 分片阈值在工具内统一处理
- 当条目数超过 500 时，按标题首字母分组输出 `index-{group}.json` 与 `manifest.json`；否则只输出 `index.json`。
- 无论何种模式都保证输出结构与前端 `loadData()` 兼容。
- 原因：前端已支持 `manifest` 回退，补上工具侧即可贯通完整链路。

## Risks / Trade-offs

- [HTML 站点结构不稳定] → 配置化 selector，并在单源抓取失败时继续处理其他源。
- [启发式标签质量一般] → 限制标签数量并优先保留源站已有分类，后续可再接 LLM 增强。
- [localStorage 异常难以稳定复现] → 将错误处理集中在持久化函数，便于后续测试注入。
- [分片分组策略不均衡] → 先按首字符实现简单方案，后续若数据规模继续扩大再优化分桶规则。
