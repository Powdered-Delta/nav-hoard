## Context

当前 `interactive-entry-workflow` 主 spec 已经覆盖了单条链接录入、显式确认写入、本地编辑器基础读写以及编辑器内书签导入入口，但编辑器本身已经发展成更完整的人工维护工具。现有实现除了基础增删改存，还支持：

- 按 URL 执行同步抓取并回填字段
- 编辑 `featured`、`featured_rank`、`hide`
- 上传本地预览图到 `public/images/previews/`
- 过滤“只看置顶”
- 批量选择、全选当前结果、批量删除
- 通过 `--host` / `--port` 开启局域网访问

这些能力直接影响人工维护体验，却没有被主 spec 明确记录。因此这次设计的目标，是把编辑器的正式规格从“最小可用维护入口”扩展为“当前真实维护工作流”，并保持边界清晰：编辑器仍然是本地维护工具，不被定义为线上部署产物，也不承担自动发布职责。

## Goals / Non-Goals

**Goals:**
- 让 `interactive-entry-workflow` 的本地编辑器规格覆盖当前真实存在的维护能力。
- 明确编辑器可以维护 `featured` / `featured_rank` / `hide` 这类条目元数据。
- 明确编辑器支持上传预览图并写入可发布的预览图元数据。
- 明确编辑器支持 `--host` / `--port` 参数，便于局域网或非默认端口访问。
- 明确编辑器支持“只看置顶”、批量选择与批量删除等列表维护动作。

**Non-Goals:**
- 不在这次变更中重做编辑器 UI 结构或样式策略。
- 不在这次变更中把编辑器变成线上部署的一部分。
- 不在这次变更中引入新的云端协作或远程数据库能力。
- 不在这次变更中为编辑器增加新的导入来源格式，除非已有实现已经支持。
- 不在这次变更中重构共享 pipeline，只补录现有编辑器行为。

## Decisions

### 1. 继续修改现有 `interactive-entry-workflow`，而不是拆出单独的 editor capability
- 方案 A：新建 `local-editor-workflow` capability。
- 方案 B：继续在 `interactive-entry-workflow` 中扩展编辑器 requirement。
- 决策：选择方案 B。
- 原因：当前编辑器仍然是交互式录入工作流的一部分，拆分会把单条录入和本地维护割裂开。

### 2. 把编辑器增强能力视为正式维护行为，而不是实现细节
- 方案 A：只保留“能打开、能保存”的最小 requirement，把其余能力留在 README。
- 方案 B：把 `featured` / `hide` / 图片上传 / 批量操作 / 局域网参数写入正式 spec。
- 决策：选择方案 B。
- 原因：这些能力直接决定人工维护路径，已经不是可忽略的 UI 细节。

### 3. 预览图上传继续建模为“本地工具写入可发布资源”
- 方案 A：只描述预览字段可编辑，不写上传行为。
- 方案 B：明确上传图片会落到 `public/images/previews/` 并生成可用的预览引用。
- 决策：选择方案 B。
- 原因：这正是当前编辑器相对普通 JSON 编辑的关键能力之一。

### 4. 局域网访问参数纳入编辑器运行 requirement
- 方案 A：把 `--host` / `--port` 视为纯 CLI 细节，不写进 spec。
- 方案 B：把它视为“本地编辑器可在不同网络/端口环境下运行”的正式能力。
- 决策：选择方案 B。
- 原因：这关系到真实使用方式，尤其是跨设备维护场景。

### 5. 批量维护能力以“筛选 + 选择 + 删除”为当前边界
- 方案 A：只写已有批量删除，不提列表筛选和只看置顶。
- 方案 B：把只看置顶、批量选择、全选当前结果、批量删除一并描述为当前列表维护能力。
- 决策：选择方案 B。
- 原因：这些动作是连贯的一组列表维护工作流，拆开描述会丢失用户操作上下文。

## Risks / Trade-offs

- [编辑器 spec 变长] → 通过把增强能力聚焦在“当前已实现的维护行为”，避免无限扩张。
- [规格触及较多 UI 交互细节] → 只记录稳定的行为边界，不约束视觉实现细节。
- [图片上传依赖本地文件系统写入] → 在 spec 中明确它是本地工具行为，不扩展为远程媒体托管能力。
- [局域网运行参数可能随实现变化调整] → 规格聚焦“支持自定义 host/port”，不锁死具体参数解析实现。

## Migration Plan

1. 更新 `interactive-entry-workflow` 主 spec，补录编辑器增强 requirement。
2. 对照当前 `editor.ts`、`editor-html.ts` 与 README，确保规格与现有实现一致。
3. 后续如需更大范围的编辑器能力重构，再通过新的 change 继续扩展。
4. 本次变更不涉及数据迁移，也不改变现有编辑器命令入口。

## Open Questions

- 是否要在后续 change 中把批量操作扩展为批量置顶、批量打标签等更强能力。
- 是否要把编辑器的样式层边界进一步纳入正式 capability，而不是只保留在文档约定中。
- 是否要在未来为编辑器增加更明确的导入审阅模式，而不是仅依赖当前列表插入方式。
