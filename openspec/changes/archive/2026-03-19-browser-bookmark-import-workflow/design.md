## Context

当前仓库已经在本地编辑器中支持浏览器书签 HTML 导入：用户上传浏览器导出的书签文件后，前端会解析 HTML 中的 `<a href>` 链接，过滤出 `http/https` URL，生成本地条目草稿并插入编辑器列表，随后再通过已有保存链路写回 `data/index.json` 和发布数据目录。

但从 OpenSpec 视角看，这项能力目前只以“编辑器支持书签导入”的形式存在于 `interactive-entry-workflow` 中，描述的是一个 UI 操作入口，而不是“浏览器书签导入”这类独立数据来源的完整边界。现在既然 `raindrop-import-workflow` 已经被单独抽成正式 capability，浏览器书签导入也需要明确：它的输入是什么、基础字段怎么映射、和共享 pipeline 的关系是什么、当前有哪些刻意不做的事情。

这个设计的重点不是重新设计导入架构，而是把“浏览器书签导入”从编辑器私有功能提升为独立来源工作流，同时保持与当前实现一致，并为后续扩展 CLI 入口或增强抓取能力保留空间。

## Goals / Non-Goals

**Goals:**
- 把浏览器书签导入定义为独立 capability，而不是只附着在编辑器能力下面。
- 明确当前最小可用输入：浏览器导出的书签 HTML 文件。
- 明确基础映射规则：从书签链接生成 URL、标题、来源域名以及默认时间字段。
- 明确导入结果最终仍要复用共享 canonical merge / write pipeline，继承归一化、去重、校验和发布输出。
- 明确编辑器仍然是现阶段的主要入口，但不是唯一语义边界。
- 为后续可能增加的 CLI 独立入口、抓取增强、目录层级映射保留清晰扩展点。

**Non-Goals:**
- 不在这次变更中实现新的 CLI 书签导入命令。
- 不在这次变更中把浏览器书签导入与 Raindrop 导入合并成统一“大导入框架” capability。
- 不在这次变更中规定书签文件夹层级一定要映射为 tags、source 分组或导航层级。
- 不在这次变更中引入自动抓取、LLM 增强或导入审阅模板作为必选步骤。
- 不在这次变更中扩展浏览器同步 API 或书签数据库直连。

## Decisions

### 1. 将浏览器书签导入建模为独立 capability，而不是继续留在编辑器 requirement 里
- 方案 A：继续只在 `interactive-entry-workflow` 里描述“编辑器支持导入书签 HTML”。
- 方案 B：把“浏览器书签导入”单独建模，再把编辑器入口视为这个 capability 的一个接入点。
- 决策：选择方案 B。
- 原因：导入来源、字段映射和去重写回逻辑本质上属于数据摄入工作流，不应只被 UI 操作入口定义；独立 capability 也更方便后续补 CLI 或批处理入口。

### 2. 当前输入边界先收敛到浏览器导出的书签 HTML 文件
- 方案 A：一开始就把 HTML、JSON、浏览器内部数据库导出等来源都纳入。
- 方案 B：先只覆盖现有已实现、可验证的书签 HTML 输入。
- 决策：选择方案 B。
- 原因：这与当前编辑器实现一致，规格不会超前于代码；后续若增加其他来源，再通过新的 delta 扩展即可。

### 3. 第一阶段只提取 `<a href>` 链接并做最小字段映射
- 方案 A：首次建模就强制要求解析文件夹层级、收藏时间、备注等全部信息。
- 方案 B：先把可稳定获取的链接、标题、来源域名、默认时间字段作为基础映射，其余信息后续再增强。
- 决策：选择方案 B。
- 原因：不同浏览器导出的 HTML 结构存在差异，但链接与标题是最稳定的公共交集；最小映射更利于保持行为稳定。

### 4. 写入阶段继续复用共享 canonical pipeline
- 方案 A：书签导入直接在编辑器状态中拼最终结构并自行写入 JSON。
- 方案 B：书签导入只负责生成条目草稿，保存时继续走现有归一化、去重、校验与发布写出路径。
- 决策：选择方案 B。
- 原因：这样能与单条录入、Raindrop 导入保持一致的数据质量和去重语义，避免出现第二套写入规则。

### 5. 当前不把抓取增强和标签推断作为浏览器书签导入的默认职责
- 方案 A：书签导入默认就触发页面抓取或 AI 增强。
- 方案 B：当前 capability 先保持基础导入职责，把抓取增强留作后续可选扩展。
- 决策：选择方案 B。
- 原因：浏览器书签导入的核心价值是把已有收藏快速带入系统；如果默认引入抓取或 AI，会显著放大时延、失败面和配置复杂度。

### 6. 现有 `interactive-entry-workflow` 需要被修改为“入口说明”，而不是完整导入定义
- 方案 A：保留原 requirement，不再区分入口与能力边界。
- 方案 B：修改原 requirement，使其只描述“编辑器提供浏览器书签导入入口”，详细导入语义迁移到新 capability。
- 决策：选择方案 B。
- 原因：这样可以避免同一能力被两个 spec 重复定义又互相漂移。

## Risks / Trade-offs

- [当前只支持 HTML 书签导出] → 通过明确输入边界避免过度承诺，后续如需 JSON / 其他格式再单独扩展。
- [未解析文件夹层级会损失部分用户整理结构] → 先保证链接导入可用，后续再评估是否把层级映射为 tags 或分组。
- [未默认抓取会导致部分导入条目标题、摘要较弱] → 由后续编辑器人工修订或未来可选增强能力补足。
- [入口与能力拆开后会增加一份 spec 维护成本] → 通过把 `interactive-entry-workflow` 明确为入口描述，降低重复定义带来的漂移风险。
- [不同浏览器 HTML 细节差异较大] → 第一阶段仅依赖最通用的 `<a href>` 提取规则，减少兼容性假设。

## Migration Plan

1. 先为 `browser-bookmark-import-workflow` 建立独立 delta spec，描述输入、映射和写回边界。
2. 同步修改 `interactive-entry-workflow`，把“书签导入” requirement 收敛为编辑器入口能力说明。
3. 后续如需要 CLI 独立入口、目录层级映射或抓取增强，再以增量 change 继续扩展。
4. 本次变更不涉及历史数据迁移，也不要求调整现有编辑器导入 UI。

## Open Questions

- 后续是否要把书签文件夹层级映射为 tags、source 分类或分组字段。
- 是否要在未来加入 CLI 独立入口，使浏览器书签导入不依赖编辑器页面。
- 是否要为浏览器书签导入增加可选抓取增强，以自动补齐摘要、标签和预览图。
- 是否要在导入前提供轻量审阅或 dry-run 输出，帮助用户先检查导入结果。
