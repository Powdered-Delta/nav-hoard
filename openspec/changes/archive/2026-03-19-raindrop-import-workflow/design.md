## Context

Raindrop 导入当前已经作为一条独立 CLI 存在，并且不是简单的 CSV 落盘脚本，而是复用了仓库现有的 canonical 写入路径、URL 抓取能力、预览图处理和去重合并逻辑。与此同时，这条链路还叠加了多种运行模式：可直接从 CSV 字段导入、可在导入时顺带抓取页面、可在抓取后用 LLM 对标签做补强，因此它已经具备独立建模为正式能力的复杂度。

这次设计的重点不是重新设计导入架构，而是明确 Raindrop 导入在当前仓库中的稳定边界：输入是什么、复用了哪些共享能力、哪些增强路径是可选的、最终写回 canonical 数据时遵守哪些规则。

## Goals / Non-Goals

**Goals:**
- 把 Raindrop 导入定义为正式的、可重复执行的数据导入能力。
- 明确导入输入支持单个 CSV 文件路径和包含 `export.csv` 的导出目录。
- 明确导入过程对共享 pipeline 的复用方式，包括草稿归一化、抓取、去重合并与写出。
- 明确 `--no-fetch`、`--llm-enhance` 和 `--featured-from-favorite` 等模式的职责边界。
- 让导入结果的统计输出成为规格中的稳定反馈，而不是实现细节偶然产物。

**Non-Goals:**
- 不在这次变更中定义 Raindrop 官方 API 集成。
- 不把浏览器书签导入并入本次能力范围。
- 不在这次变更中扩展新的模型配置体系，只记录当前依赖本地配置文件的增强方式。
- 不在这次变更中重做导入 CLI 的参数风格或命令入口名称。

## Decisions

### 1. 保持 Raindrop 导入为独立 capability，而不是并入 `interactive-entry-workflow`
- 方案 A：把 Raindrop 导入当作编辑器/录入链路的一部分补录。
- 方案 B：把它建模为独立 capability。
- 决策：选择方案 B。
- 原因：Raindrop 导入是批量数据摄入流程，输入、输出、错误处理和增强路径都与单条录入不同，独立 capability 更利于后续演化。

### 2. 输入解析先兼容“文件”和“目录”，不额外扩展更多导出格式
- 方案 A：只支持 CSV 文件。
- 方案 B：支持 CSV 文件和包含 `export.csv` 的导出目录。
- 决策：选择方案 B。
- 原因：这符合当前实现，也能覆盖 Raindrop 用户最常见的本地导出使用方式。

### 3. 导入写入必须继续复用共享 pipeline，而不是自行写 JSON
- 方案 A：导入脚本直接拼装最终 JSON 并写入文件。
- 方案 B：导入脚本只负责生成草稿，再调用共享 `mergeDraftEntries` 写入 canonical 数据。
- 决策：选择方案 B。
- 原因：这样可以自动继承现有的 URL 规范化、preview 归一化、去重、校验与发布输出，避免出现第二套写入规则。

### 4. 抓取增强与 LLM 增强都保持为可选层
- 方案 A：导入必须抓取，并在配置存在时自动走 LLM。
- 方案 B：基础导入先保证仅靠 CSV 字段就能完成；抓取和 LLM 都是显式开启的增强层。
- 决策：选择方案 B。
- 原因：这样能保证导入在离线、弱网或未配置模型时仍然可用，也更符合当前 CLI 参数设计。

### 5. 标签策略以“保留原标签，再合并增强标签”为准
- 方案 A：抓取或 LLM 结果完全覆盖 Raindrop 原标签。
- 方案 B：以原标签为基础，再合并抓取/LLM 建议标签并去重。
- 决策：选择方案 B。
- 原因：Raindrop 原标签往往承载用户手工整理结果，不应被增强过程无条件覆盖。

### 6. 收藏标记映射为推荐状态保持显式开关
- 方案 A：默认把 Raindrop 的 `favorite=true` 映射为 `featured=true`。
- 方案 B：仅在用户显式传入 `--featured-from-favorite` 时才进行映射。
- 决策：选择方案 B。
- 原因：Raindrop 的收藏语义不一定等同于 NavHoard 的作者推荐语义，保留显式开关更安全。

## Risks / Trade-offs

- [CSV 字段质量不稳定] → 通过可选抓取层补足标题、摘要、来源和预览图，但保留无抓取模式作为兜底。
- [LLM 配置不完整或接口不稳定] → 仅在显式开启且配置完整时使用 LLM，否则退回非 LLM 导入并给出明确提示。
- [批量导入可能引入大量重复项] → 继续依赖共享 merge/write 路径做 URL 归一化和重复合并。
- [用户对 `favorite` 语义理解不同] → 通过显式参数控制推荐映射，避免默认行为过强。
- [导入统计与内部置信度耦合] → 后续若要让统计更稳定，可能需要把“来源阶段”与“confidence”拆开建模。

## Migration Plan

1. 先为 `raindrop-import-workflow` 建立正式 delta specs，确认当前实现边界。
2. 评审后再决定是否需要调整 CLI 输出、标签统计方式或配置命名。
3. 如需后续增强，再新增 change 处理更多来源格式、官方 API 接入或更细粒度的导入审阅。
4. 本次变更不涉及历史数据迁移，属于规格补录与能力归档。

## Open Questions

- 是否需要把当前基于 `confidence` 推断“抓取成功/LLM 增强”的统计方式改成显式阶段字段。
- 是否要在后续 change 中为导入流程增加 dry-run 或审阅模板输出能力。
- 是否要把 Raindrop 封面图映射规则扩展为更明确的预览图策略规格。
