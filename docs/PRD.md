# NavHoard / 集径 - PRD

- 日期: 2026-03-11
- 版本: v0.3
- 状态: 迭代中

## 1. 背景与目标
1. 用户收藏大量链接后很少回看，信息利用率低。
2. 需要一个可收集、可筛选、可再发现的轻量导航收藏页。
3. 除了被动展示公开数据，还需要支持“人工策展式新增条目”，让用户能用对话方式快速补充内容。
4. 同时支持 GitHub Pages 二级路径部署和博客子路由集成。

## 2. 目标用户与使用场景

### 用户画像
1. 高频浏览技术/资讯网站的个人用户。
2. 维护公开导航站的内容策展者。
3. 依赖自动化抓取与整理的开发者。
4. 希望通过 AI/Agent 辅助半自动录入内容的个人项目维护者。

### 用户故事
- US-1: 作为技术开发者，我想通过关键词快速找到之前收藏过的文章链接，以便减少重复搜索时间。
- US-2: 作为内容策展者，我想按标签筛选特定领域的链接，以便整理主题化的推荐列表。
- US-3: 作为个人用户，我想把感兴趣的链接标记收藏并随时查看，以便区分“已读”和“待读”。
- US-4: 作为开发者，我想通过手动执行抓取流程来提交 PR 并校验数据，以便在需要时更新内容而不依赖完全自动化。
- US-5: 作为维护者，我想在会话窗口中输入一个链接，由 Agent 帮我抓取、生成条目草稿、让我确认修改后再写入数据源，以便快速新增高质量条目。
- US-6: 作为维护者，我想在新增条目后继续由 Agent 询问我是否要本地测试或直接提交到仓库，并在缺少配置时得到引导，以便形成完整的维护闭环。

## 3. 产品定位
1. 带轻策展气质的现代化收藏导航站。
2. 前端只读公开数据，用户私有状态本地保存。
3. 数据维护支持两条路径：
   - 批量更新：通过 `copenclaw` 抓取多个源。
   - 单条录入：通过 Agent 交互式添加链接条目。
4. Agent 是维护工作流的交互层，抓取、抽取、去重、校验、写入由底层通用 pipeline 完成。

## 4. 范围与优先级

| 优先级 | 功能 | 说明 |
|--------|------|------|
| P0 | 首页卡片流 | 标题、简介、标签、来源、更新时间 |
| P0 | 关键词搜索与标签筛选 | 支持排序（最新/相关） |
| P0 | 数据读取 | 从 `data/index.json` 或 `manifest.json` + 分片加载 |
| P0 | 响应式 UI | 移动端 / 桌面端 |
| P1 | 本地收藏 | `localStorage`，支持“只看收藏”视图 |
| P1 | About / 空状态 | 说明入口、错误提示、无结果提示、收藏为空引导 |
| P1 | 批量更新流程 | 手动触发 `copenclaw`：抓取 → 去重 → 生成摘要/标签 → 校验 → 写入 |
| P1 | 单链接交互式入库 | Agent 引导用户输入 URL、抓取内容、返回模板、确认修改、写入数据源 |
| P2 | 仓库操作辅助 | 新增条目后，Agent 询问本地测试或提交仓库；若缺少配置则引导配置 |
| P2 | 真实 LLM 增强 | 可选接入 OpenAI 兼容接口，为摘要/标签生成提供增强模式 |

## 5. 非目标
1. 用户账号与云同步。
2. 评论、点赞、社交互动。
3. 后端服务与数据库。
4. 复杂推荐算法。
5. 完全无人值守的自动录入；单链接入库必须保留人工确认环节。

## 6. 信息架构

### 6.1 前端首页
1. 单页面应用，包含：
   - 搜索输入框 + 标签筛选器
   - 链接卡片流（可切换“全部”与“我的收藏”）
   - `About` 按钮（显示收录规则与更新说明）
2. 所有浏览功能在首页完成，无页面跳转。

### 6.2 维护工作流
1. 批量维护：维护者手动运行 `copenclaw`。
2. 单条维护：维护者在会话窗口中调用“新增条目”能力。
3. Agent 负责对话与确认，底层 pipeline 负责抓取、提取、去重、校验、写入。

## 7. 关键体验要求
1. 风格现代、轻量、可快速加载。
2. 统一设计 Token（颜色、圆角、阴影、间距），通过 CSS 自定义属性管理。
3. 卡片交互有轻动效（hover/focus/筛选过渡）。
4. 可访问性：键盘可操作，WCAG 2.1 AA 对比度达标。
5. 空状态设计：
   - 搜索无结果：显示“未找到匹配内容”，并建议清空筛选条件。
   - 数据加载失败：显示友好错误提示和重试按钮。
   - 收藏为空：引导用户回到首页浏览并收藏。
6. SEO 基础：静态 `<title>`、`<meta description>`、Open Graph 标签。
7. 单链接入库体验必须以“先预览、后确认、再写入”为基本原则，避免静默写库。

## 8. 单链接交互式入库能力

### 8.1 核心流程
1. 用户启动会话窗口并调用“新增条目”能力。
2. Agent 引导用户输入链接。
3. Agent 调用底层抓取与抽取 pipeline，尝试获取页面标题、正文摘要、来源、时间、候选标签。
4. 无论成功或失败，Agent 都返回统一模板给用户检查。
5. 用户修改模板中的字段。
6. Agent 解析用户最终版本，执行去重、校验并写入数据源。
7. Agent 继续询问：
   - 是否需要本地测试；
   - 是否需要直接提交到仓库；
   - 若 git / token / remote 等配置缺失，则给出引导。

### 8.2 模板要求

#### 成功模板
- URL
- 标题
- 摘要
- 标签
- 来源域名
- 抓取状态（成功 / 部分成功）
- confidence（可选）
- 用户确认说明

#### 失败模板
- URL
- 抓取状态（失败）
- 失败原因（如网络错误、反爬、正文为空、解析失败）
- 待用户手动补充的字段：标题、摘要、标签、来源

### 8.3 交互约束
1. Agent 不得在未经用户确认前直接写入数据源。
2. 若抓取失败，仍须允许用户手动填写并完成入库。
3. 若检测到重复 URL，应提示用户并给出合并/覆盖后的结果。
4. 新增条目后，Agent 应明确说明写入了哪个文件、是否建议运行本地验证。

## 9. 技术设计

### 9.1 技术选型
| 类目 | 选型 | 理由 |
|------|------|------|
| 构建工具 | Vite | 开箱即用、构建快、生态成熟 |
| UI 框架 | Vanilla TS + Lit（Web Components） | 轻量、无运行时依赖、可嵌入博客 |
| CSS | CSS 自定义属性 + 原生 CSS | 零依赖、与 Web Components 天然兼容 |
| 搜索 | MiniSearch | 轻量全文索引，支持模糊匹配 |
| 批量抓取 | `copenclaw` CLI | 便于本地手动执行和 CI 复用 |
| 单链接录入 | Skill + 通用 pipeline | Skill 负责编排交互，pipeline 负责执行逻辑 |

### 9.2 架构分层
1. `frontend`: 列表渲染、搜索筛选、收藏、说明入口。
2. `content-refresh-pipeline`: 抓取、提取、去重、摘要/标签生成、校验、写入。
3. `agent skill`: 对话式新增条目工作流。
4. `repo ops`: 可选的测试、提交、推送辅助。

### 9.3 单链接入库能力的实现原则
1. Skill 与 CLI / pipeline 共享同一套抽取、去重、校验与写入逻辑。
2. Skill 只做交互编排，不复制业务规则。
3. LLM 只是 enrichment 的一种实现方式，不绑定具体供应商。
4. 在未配置 LLM 时，系统应自动回退到规则法摘要/标签生成。

## 10. 数据方案

### 10.1 公共数据
- 规范上的主数据源：`data/index.json`
- 前端运行时数据：`public/data/index.json` 及可选分片文件
- 当数据量超过 500 条时，生成：
  - `public/data/manifest.json`
  - `public/data/index-{group}.json`

说明：后续实现中应进一步统一“仓库主数据源”和“前端发布数据”的生成关系，避免双写歧义。

### 10.2 私有数据
- 存储位置：`localStorage`
- key 前缀：`navhoard:`
- 存储上限处理：捕获 `QuotaExceededError`，提示用户清理旧收藏。

### 10.3 条目 Schema

```jsonc
{
  "id": "string",          // 必填，URL 的 SHA-256 前 12 位 hex
  "url": "string",         // 必填，规范化后的完整 URL
  "title": "string",       // 必填，最长 120 字符
  "summary": "string",     // 必填，最长 300 字符
  "tags": ["string"],      // 必填，0~5 个标签，每个最长 20 字符
  "source": "string",      // 必填，来源站点域名
  "created_at": "string",  // 必填，ISO 8601
  "updated_at": "string",  // 必填，ISO 8601
  "confidence": 0.0         // 可选，摘要/标签生成置信度
}
```

### 10.4 去重规则
1. URL 规范化：小写 host、去除 trailing slash、去除 `utm_*` / `ref`、统一 `http` → `https`。
2. 基于规范化 URL 的 SHA-256 生成 `id`，相同 `id` 视为重复。
3. 冲突合并策略：保留 `updated_at` 更新的条目，并合并标签去重。

## 11. 数据更新流程

### 11.1 批量更新（`copenclaw`）
1. 读取 `data/sources.yaml`。
2. 抓取启用的数据源（RSS / HTML）。
3. 生成摘要和标签：
   - 优先使用规则法；
   - 若配置了 LLM，可切换到 LLM 增强模式。
4. 执行去重与 JSON Schema 校验。
5. 写入前端数据文件，必要时生成分片与 `manifest.json`。
6. 可选继续执行本地测试或仓库提交。

### 11.2 单链接新增（Agent）
1. 用户提供 URL。
2. pipeline 抓取并提取页面内容。
3. 生成草稿条目。
4. Agent 以模板形式回显给用户修改。
5. 用户确认后写入数据源。
6. Agent 询问是否运行本地测试、是否提交仓库。

### 11.3 错误与提示
1. 抓取失败时，必须输出可操作的错误原因。
2. 校验失败时，必须指出具体字段问题。
3. 缺少提交配置时，Agent 必须引导用户补齐，而不是静默跳过。

## 12. 配置与集成要求

### 12.1 LLM / 抓取能力配置
1. 系统应支持通过配置文件或环境变量注入 LLM API Key。
2. 未配置 LLM 时，系统应继续工作，但以规则法生成摘要和标签。
3. 单链接入库与批量更新应共用 enrichment 配置。

### 12.2 仓库操作配置
1. 若用户选择“直接提交到仓库”，系统需检查至少以下条件：
   - git 仓库可用；
   - `user.name` / `user.email` 已配置；
   - remote 存在；
   - 如需推送，认证信息可用。
2. 若条件不满足，Agent 需输出明确引导步骤。

## 13. 非功能要求

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| LCP | <= 2.5s（4G） | Lighthouse |
| 5k 条搜索响应 | < 200ms | Performance API |
| JS Bundle 大小 | < 50KB gzip | 构建产物分析 |
| Lighthouse Performance | >= 90 | Lighthouse |
| 交互式入库确认时间 | 单条新增全流程 <= 3 分钟 | 人工验证 |

### 性能策略（5k+ 条记录）
1. 首次加载构建 MiniSearch 索引，后续搜索在内存中完成。
2. 搜索输入使用防抖。
3. 大数据量下启用分片加载。

## 14. 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| 1 | 站点在 GitHub Pages 和博客子路径下资源路径正确 | 手动部署验证 |
| 2 | 搜索、标签筛选、收藏视图正常工作 | 手动测试 |
| 3 | About、错误态、无结果态、收藏为空态可正确展示 | 手动测试 |
| 4 | `copenclaw` 可抓取 RSS / HTML 源并产出有效 JSON | CLI 验证 |
| 5 | 数据量超过 500 条时可生成 `manifest.json` 和分片文件 | CLI 验证 |
| 6 | Agent 单链接入库流程可完成“输入 URL → 抓取 → 模板确认 → 写入” | 端到端演示 |
| 7 | 抓取失败时仍可由用户手动补齐字段并完成入库 | 端到端演示 |
| 8 | 新增条目后可继续选择本地测试或仓库提交 | 会话演示 |
| 9 | 缺少 git / LLM 配置时能给出明确引导 | 会话演示 |
